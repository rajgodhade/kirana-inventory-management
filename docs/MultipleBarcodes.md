# Multiple Product Barcodes (Phase 13B)

Phase 13B replaces the single `Product.Barcode` string with a one-Product-to-many-`ProductBarcode`
model, so a manufacturer EAN-13, a second EAN after a supplier repack, and an internally generated
code for loose goods can all scan to the same product. The POS scan path stays a single indexed
equality probe.

## What stays the same

- **Scanning is unchanged at the till.** One scan adds exactly one unit, and every code a product
  owns resolves to that same product. Nothing about the billing flow changes.
- **Every existing barcode keeps working.** The migration turns each product's old barcode into its
  primary, active `ProductBarcode` — whatever scanned to a product before still does, and label
  printing still defaults to the same value.
- **Label printing defaults to the primary**, which for every migrated product is the code it
  already had.
- **`PermissionKeys.ProductsEdit`** governs barcode changes. No new permission key was introduced.

## The model

`ProductBarcode` holds:

| Field | Purpose |
| --- | --- |
| `Value` | The code as entered — used for display and printing. Trimmed, but case preserved. |
| `NormalizedValue` | `Value` trimmed + upper-invariant. The uniqueness key, and the column every lookup queries. |
| `Symbology` | `Ean13` or `Code128`, stored rather than recomputed per row. |
| `IsPrimary` | The product's default code for label printing. Exactly one per product. |
| `IsInternal` | True when generated by the app rather than read off packaging. |
| `IsActive` | False = retired: still known, but will not scan at billing. |
| `Notes` | Free text (e.g. "old supplier pack"). |

`Product.Barcode` was **removed outright**, not kept as a compatibility shim. A shim is precisely
what produced the orphaned `IsTaxInclusive` column that silently broke product creation against real
databases; deleting the property made the compiler enumerate all ~35 call sites instead.

## Uniqueness

Uniqueness is **case-insensitive and store-wide**, enforced at three layers:

1. `BarcodeNormalizer.Normalize` — the single definition of "the same barcode", shared by the EF
   configuration, the services, the importer, and the backfill migration. Upper-**invariant** on
   purpose: `ToUpper()` under a Turkish locale maps `i` to `İ`, which would make the stored key
   depend on the machine's regional settings.
2. `BarcodeService.EnsureAvailableAsync` — checked before every mutation, so the user gets a clear
   message naming the conflicting product rather than a database error.
3. A unique index on `NormalizedValue`.

This resolved a real pre-existing inconsistency: `BarcodeService` compared case-sensitively in SQL
while `ProductImportService` deduped with `OrdinalIgnoreCase` dictionaries, so `abc123` and `ABC123`
were the same value to the importer and two different values to the uniqueness check.

The unique index is deliberately **unfiltered** — it covers retired barcodes too. A retired code
keeps ownership of its value, so reactivating it can never resurrect a duplicate.

## The one-primary rule

Every product with barcodes has exactly one primary, guaranteed by:

- A **filtered unique index** `IX_ProductBarcodes_ProductId_Primary` on `ProductId WHERE IsPrimary = 1`,
  making this a database invariant rather than a convention.
- **Auto-primary** on a product's first barcode, regardless of what the caller asked for — so
  "has barcodes but no primary" is unreachable through the service.
- **Auto-promotion** when a primary is retired: the oldest remaining active barcode takes over. When
  nothing else is active the retired row keeps the flag, so a product never ends up with barcodes
  but no primary.

### Statement ordering matters

SQLite evaluates a filtered unique index **per statement**, and EF orders its `UPDATE`s by primary
key. So a batched demote-then-promote fails whenever the newly promoted row has the lower `Id` —
which is the common case, since auto-promotion picks the *oldest* remaining barcode.

`SetPrimaryAsync` and the retire path therefore use **two saves**: demote first, then promote. That
leaves a brief zero-primary window rather than a hard failure — zero primaries is recoverable and
invisible to billing (lookup never filters on `IsPrimary`), whereas two primaries is rejected
outright. `AddBarcodeAsync` is safe as a single save because its promotion is an `INSERT` and EF
issues `UPDATE`s before `INSERT`s.

Reactivating a retired barcode never reclaims primary: the retired row may still carry a stale flag
that another code has since taken. Reactivation restores the code, not its rank.

## Scanner behavior

`BarcodeLookupService.LookupAsync` (the POS path) skips **both** inactive barcodes and inactive
products. A retired code and a discontinued product must each refuse to enter a cart.

`LookupDiagnosticAsync` sees everything and reports *why* a code will not scan. This is what the
Barcode Scan test page uses, so a retired code shows "known but retired, will not scan at billing"
instead of a misleading "not found" — the difference between a five-minute fix and a confusing dead
end for a shopkeeper.

Sales-return lookup deliberately does **not** filter `IsActive`: someone returning goods months later
may well scan a since-retired code, and finding the original sale is the whole point.

`ProductService.SearchAsync` filters `IsActive` in **both** its exact-barcode bucket and its partial
`LIKE` bucket. POS search feeds straight into the cart, so a retired code that still surfaced its
product through the partial match would defeat retirement entirely — the operator types the old code,
presses Enter, and sells against it anyway. Only the exact bucket filtered at first; this was caught
by live E2E rather than by unit tests, and is now pinned by
`SearchAsync_DoesNotSurfaceAProduct_ByItsRetiredBarcode`.

## Import format

The CSV column is **`Barcodes`**, with `barcode`, `ean`, `upc`, `eans`, and `barcodelist` kept as
aliases so files exported by earlier versions still import unchanged.

- Multiple codes in one cell are separated by `|` — a pipe never appears in a retail EAN/UPC/Code128
  value and needs no CSV quoting, unlike a comma. It matches what `DataExportService` emits, so an
  export round-trips back through the importer.
- A leading `*` designates the primary: `8901030826501|*5012345678900`. The marker is stripped before
  validation; it is not part of the code. Marking more than one is an error.
- With no marker, the first code becomes primary.

Reconciliation is **additive, never destructive**. An import file is rarely the complete truth about
a product, so codes the file omits are left alone rather than silently retired. An import also never
demotes a primary the operator chose in the app.

Barcode staging happens inside `CommitAsync` and only ever stages entities — the whole import still
shares one `SaveChangesAsync`, so a rejected row leaves nothing behind.

A row whose barcode matches an existing product is an **update** of that product, not an error —
that is what makes re-importing a corrected file work. Only a row that names one product by SKU while
carrying a *different* product's barcode is a genuine conflict, and that is caught during preview
rather than left to the unique index, where it would roll back every other valid row in the file.

## Migration

`20260813100000_AddProductBarcodes` is the repo's first `migrationBuilder.Sql(...)`. The step order
is **not** what `dotnet ef` scaffolds — EF put the `DropColumn` first, which would have destroyed
every existing barcode. The correct order is:

1. create table
2. **backfill**
3. create indexes
4. drop the old index
5. drop the column

The unique index is created *after* the backfill on purpose. The old index on `Products.Barcode` was
case-**sensitive**, so a legacy pair like `abc123`/`ABC123` could coexist there while violating the
new case-insensitive uniqueness. Resolving that with `GROUP BY UPPER(TRIM(...))` inside the `INSERT`
keeps the migration non-interactive; creating the index first would abort the upgrade half-applied.

> **`GROUP BY` caveat.** The backfill pairs `MIN(p.Id)` with bare `TRIM(p.Barcode)` columns. That is
> safe only because of a documented SQLite guarantee: in a query with a single `MIN()`/`MAX()`
> aggregate, bare columns take their values from the row that produced that min/max. Removing
> `MIN()`, adding a second aggregate, or porting this to another engine breaks the guarantee and can
> pair one product's id with another's barcode text.

Symbology is written as `Code128`, then a second `UPDATE` flips unambiguous 13-digit codes to
`Ean13`. Check digits are not reasonably computable in SQLite SQL; the divergence is cosmetic (the
renderer draws a 13-digit value as EAN-13 regardless) and self-corrects on the next edit.

`Down()` genuinely reverses: it re-adds the column at its original width of 60 — reproducing the
prior schema exactly rather than "fixing" it — restores each product's primary value, recreates the
old index, and drops the table. Alternate barcodes are lost, which is inherent to reverting to a
one-barcode model; this is a recovery path, not a routine one.

### Testing the backfill

The shared test fixtures use `EnsureCreated()`, which builds from the entity model and never executes
a single line of migration SQL — so the backfill is invisible to almost every test. It is covered by
migrating to the *previous* migration via `IMigrator`, raw-inserting legacy `Products` rows
(including NULL, blank, and a case-only-duplicate pair), then migrating forward and asserting the
resulting rows.

Every migration is additionally rehearsed against a **copy of the real database** before being
applied anywhere, via the `KIRANA_MIGRATION_DB` environment override.

## Length

Barcodes are capped at **48** characters. EF previously allowed 60 while `BarcodeService` rejected
anything over 48, making 49–60 unreachable dead headroom — so standardizing on 48 cannot lose data.
`BarcodeNormalizer.MaxBarcodeLength` is the single source of that number, and the EF column is sized
from it so the two cannot drift apart again.

## Audit trail

All barcode actions record against `nameof(Product)` and the **product's** id, so the trail groups
under what operators actually search for: `BarcodeAdded`, `BarcodeChanged`, `BarcodeDeactivated`,
`BarcodeReactivated`, `BarcodePrimaryChanged`, `BarcodeGenerated`, `BarcodeRemoved`, and
`BarcodeAssigned` (retained from the pre-13B wrapper so existing history stays searchable).

## Limitations and deferred work

- **No packaging-specific barcode → quantity conversion.** `ProductBarcode` deliberately has no
  quantity/multiplier field. A nullable multiplier that nothing at the till honored would be a
  correctness trap: scanning a "case of 12" barcode would silently add 1. Doing this properly means
  threading a quantity through the scan path, the cart, returns, and stock movements — a phase of its
  own, not a column.
- **No physical stock counting or inventory adjustment workflows** (Phase 13C+).
- **No mobile or Bluetooth scanning.** USB HID scanners only, as before.
- **Barcodes do not flow through `UpdateProductRequest`.** They persist immediately via
  `IBarcodeService` while the edit dialog is open, which is a deliberate trade: it avoids duplicating
  the uniqueness and primary invariants in a second place. The dialog surfaces this with a visible
  cue, since it means barcode edits are not undone by cancelling the dialog.
